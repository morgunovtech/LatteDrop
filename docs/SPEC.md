# LatteDrop — техническое задание

**Продукт:** личное macOS-приложение для real-time музыкальной визуализации в духе MilkDrop.
**Версия документа:** 2.0 — после уточнения рамок
**Дата:** 30 августа 2026
**Исполнитель:** автор проекта + Claude Code

---

## 1. Рамки проекта

Приложение **для себя, не публикуется**. Отсюда рамки, которые снимают большой объём работы:

| Решение | Следствие |
|---|---|
| Только macOS 26 Tahoe, только Apple Silicon | Один бэкенд захвата звука, без ScreenCaptureKit-фолбэка, без x86_64, без бюджетов для Intel |
| Не публикуется | Нет нотаризации, Sparkle, App Store, лицензионного слоя, телеметрии, локализации, маркетингового онбординга |
| Импорт `.milk` не нужен | Нет парсера EEL2, нет транспиляции HLSL→MSL, нет SPIRV-Cross, нет вопроса с projectM и LGPL |
| Трекер только на DSP | Нет Core ML, нет вопроса с лицензией весов; интерфейс наблюдений оставлен открытым на будущее |
| Обычное окно рядом с работой | Нет режима обоев, скринсейвера, меню-бар-агента, мультимониторной логики. Полный экран — как дешёвый бонус |
| Настройки минимальные | Панель на один экран; тонкая настройка пресетов — через JSON с hot-reload |
| Записи видео нет | Нет модуля `AVAssetWriter` |

**Главный приоритет — точность попадания в бит.** Всё остальное уступает ему при конфликте.

### 1.1. Сценарий использования

Окно рядом с рабочими окнами, музыка играет из любого приложения, слушается через **AirPods, встроенные динамики или проводной интерфейс**. Жанры — с двух противоположных концов: **электроника / техно / хаус** (жёсткая сетка 4/4) и **эмбиент / классика / джаз** (часто вообще без выраженного бита). Приложение обязано хорошо работать на обоих концах и само понимать, на каком оно сейчас находится.

### 1.2. Визуальные направления

Все четыре выбранных направления сводятся к **трём** рендер-подсистемам — это важно для оценки объёма:

| Направление | Подсистема |
|---|---|
| Классический MilkDrop: туннели, следы, зеркала | **A. Feedback-растр:** буфер предыдущего кадра + warp/zoom/rotate |
| Ретро: осциллограф, CRT, вектор, Лиссажу | **B. Векторный рендер:** полилинии с фосфорным свечением и послесвечением |
| Геометрия и минимализм | **B.** (та же подсистема — линии, сетки, строгие формы) |
| Органика: жидкость, дым, частицы | **C. Compute-частицы:** флоу-филд, до 1 млн частиц, адвекция |

Подсистемы A и B дают восемь из десяти пресетов и стоят дёшево; C — самая дорогая, делается последней.

## 2. Архитектура и контракты модулей

```
AudioCapture ──PCM+hostTime──▶ AnalysisEngine ──FeatureFrame──▶ TimelineBus
                                                                     │
                                              MusicState(at: t) ◀────┘
                                                     │
                          PresetStore ──Preset──▶ Renderer ──▶ MTKView
```

Четыре потока: real-time IO Core Audio, поток анализа (hop 512), рендер-поток на `CAMetalDisplayLink`, main для UI.

### 2.1. Ключевые контракты

```swift
/// Снимок анализа одного окна. Публикуется потоком анализа ~86 раз в секунду.
struct FeatureFrame {
    let hostTime: UInt64          // mach_absolute_time середины окна анализа
    let level: Level              // rms, peak, loudnessShort, crest
    let bands: Bands              // 24 mel + агрегаты bass/lowMid/mid/high
    let spectral: Spectral        // centroid, flatness, rolloff, flux
    let onsets: Onsets            // kick, snare, hats, tonal — сила 0…1
    let rhythm: Rhythm            // bpm, confidence, beatPhase, barPhase, beatIndex, isDownbeat
    let harmony: Harmony          // chroma[12], key, mode, chordChange
    let dynamics: Dynamics        // energyDelta, buildUp, drop, sectionChange, isSilent
    let character: Character      // см. §5 — вычисленный характер реакции
}

/// Кольцевой буфер кадров с интерполяцией и экстраполяцией.
/// Единственный мост между анализом и рендером.
final class TimelineBus {
    func publish(_ frame: FeatureFrame)
    /// Состояние музыки на произвольный момент, в том числе в будущем.
    /// Фаза доли экстраполируется, остальные поля интерполируются.
    func state(at hostTime: UInt64) -> MusicState
}

/// Всё, что видит рендер. Никаких прямых обращений к анализу из шейдеров.
struct MusicState {
    let beatPhase: Float          // 0…1, непрерывная, экстраполированная
    let barPhase: Float           // 0…1 по такту
    let beatConfidence: Float     // 0…1, ниже 0.35 — режим свободного ритма
    let bpm: Float
    let level, bass, mid, high: Float     // сглаженные и нормализованные
    let kick, snare, hat: Float           // импульсы онсетов с затуханием
    let buildUp, drop, sectionChange: Float
    let hue: Float                // из тональности
    let motionScale: Float        // из §5, общий множитель «характера»
}

protocol Visual: AnyObject {
    static var id: String { get }
    func reload(params: PresetParams) throws       // hot-reload без пересоздания
    func encode(_ cb: MTLCommandBuffer, state: MusicState, targets: RenderTargets)
}
```

`MusicState` — единственная точка контакта между аудио и графикой. Любой пресет получает уже готовую, отнормированную, предсказанную на нужный момент картину музыки и не занимается DSP.

## 3. Модель времени и A/V-синхронизация

Это ядро проекта. Три независимые задачи, все обязательны.

### 3.1. Единая шкала

Каждый сэмпл и каждый `FeatureFrame` несут `mach_absolute_time` из `AudioTimeStamp`, а не время обработки. Рендер получает `targetPresentationTimestamp` от `CAMetalDisplayLink` — момент реального появления кадра на экране.

### 3.2. Компенсация задержки вывода — приоритет №1

Вы слушаете через AirPods, поэтому это главный практический риск проекта: без компенсации визуал промахивается на четверть секунды и вся работа над трекером бессмысленна.

```
Δout = kAudioDevicePropertyLatency + kAudioDevicePropertySafetyOffset
     + bufferFrameSize / sampleRate + kAudioStreamPropertyLatency
     + transportLatency
```

| Тракт | Δout | Как получаем |
|---|---|---|
| Встроенные динамики | 5–15 мс | Свойства устройства, достоверно |
| Проводные / USB-интерфейс | 5–25 мс | Свойства устройства, достоверно |
| AirPods и другой Bluetooth | 150–250 мс | Свойства + таблица профилей + ручная поправка |

Требования:
- Δout пересчитывается при старте и при каждой смене устройства вывода (подписка на `kAudioHardwarePropertyDefaultOutputDevice`).
- Визуал **задерживается** на Δout: рендер запрашивает `bus.state(at: targetPresentationTimestamp - Δout)`.
- Слайдер ручной поправки −300…+300 мс, хоткеи `[` и `]` с шагом 5 мс, применённое значение видно в HUD.
- **Калибровочный режим:** метроном-точка в HUD плюс генерация щелчка на каждую долю в отдельный выход — пользователь на слух совмещает щелчок и вспышку. Значение запоминается для каждого устройства вывода по его UID.

### 3.3. Предсказание доли вместо реакции

Задержка анализа 20–80 мс, поэтому реактивный визуализатор опаздывает всегда. Фазовый осциллятор доли рендерит кадр по предсказанной фазе:

```
phase(t) = wrap( phase_last + (t − t_last) × bpm / 60 )
```

PLL мягко подтягивает осциллятор к наблюдаемым онсетам с ограничением дрейфа 4 % за долю — пропущенный или ложный онсет не дёргает картинку.

**Критерий:** медианная ошибка ≤ 20 мс, P90 ≤ 45 мс на бенчмарке §9.2, отдельно проверено на AirPods.

## 4. Захват звука

Единственный бэкенд: **Core Audio Process Tap** (macOS 14.2+, стабильно с 14.4 — на Tahoe доступен полностью).

- `CATapDescription` в режиме system-wide **unmuted** — звук продолжает идти в наушники + `AudioHardwareCreateProcessTap` + `AudioHardwareCreateAggregateDevice`, чтение через `AudioDeviceIOProc`.
- Разрешение TCC: System Audio Recording. В `Info.plist` — `NSAudioCaptureUsageDescription`.
- Поддержка 44.1 / 48 / 96 кГц, даунмикс в моно для анализа; ресемплинг в 44.1 кГц.
- IO-колбэк только копирует в lock-free SPSC ring buffer: без аллокаций, локов, логирования и ARC-трафика.
- Смена устройства вывода, sleep/wake, смена sample rate, отключение AirPods, остановка tap'а системой → автоматическое пересоздание пайплайна за ≤ 300 мс, без падения и без перезапуска приложения.
- Тишина: RMS ниже −60 дБFS дольше 2 с → плавное затухание, FPS до 30, сброс трекера темпа.

> **Практический нюанс сборки.** TCC привязывает выданное разрешение к подписи приложения. При пересборке с ad-hoc подписью разрешение слетает и запрашивается заново на каждом запуске. Настроить **стабильный самоподписанный сертификат** в проекте с первого дня — иначе разработка превратится в бесконечные диалоги системы.

Метаданные трека (Now Playing) **не используются**: с macOS 15.4 `MediaRemote` закрыт для сторонних приложений. Смена трека определяется по аудио (§5.4).

## 5. Аудиоанализ

### 5.1. Базовый слой

Accelerate / vDSP. Основное окно 2048 сэмплов (46 мс), hop 512 (11.6 мс), окно Ханна. Дополнительное короткое окно 256 / hop 128 для транзиентов даёт точность онсетов ≤ 3 мс.

Фичи — см. `FeatureFrame` в §2.1. Все нормализуются **адаптивно**: скользящее окно 10 с, перцентили 5/95 — тихая фортепианная запись и выжатый мастер техно дают одинаковый диапазон реакции. У каждой фичи два выхода: `raw` и `smoothed` с attack/release 5 / 120 мс.

### 5.2. Онсеты

Спектральный поток с полуволновым выпрямлением по mel-полосам плюс фазовая девиация для тональных инструментов. Четыре раздельных детектора: бочка 20–120 Гц, снейр и хлопки 150–900 Гц, хай-хэты 4–12 кГц, тональный слой 200 Гц–4 кГц.

### 5.3. Темп и фаза

- Автокорреляция огибающей онсетов и гребенчатые фильтры на окне 6 с, диапазон 60–200 BPM.
- Разрешение октавной неоднозначности с приоритетом 90–160 BPM и проверкой метрической согласованности.
- Гистерезис: смена оценки только при устойчивом преимуществе новой гипотезы дольше 1.5 с.
- Фазовый осциллятор + PLL (§3.3). Определение размера такта и позиции сильной доли по бас-энергии и смене гармонии.
- **Режим свободного ритма** при `confidence < 0.35`: бит-сетка отключается, вся модуляция идёт от энергии и гармонии. Для эмбиента и классики это основной режим, и он обязан выглядеть осмысленно, а не как сломанный техно-визуализатор.

### 5.4. События

- `sectionChange` — новизна по матрице самоподобия MFCC/chroma на окне 30 с.
- `buildUp` — рост центроида, RMS и плотности онсетов за 4–16 тактов.
- `drop` — резкий возврат баса после нарастания.
- `trackChange` — резкая смена тембрового профиля с паузой; сбрасывает трекер темпа.

### 5.5. Автоматический характер реакции

Реакция должна сама подстраиваться под музыку: техно бьёт резко, эмбиент дышит медленно. Вычисляется на каждом кадре:

```
character.motionScale   = f(beatConfidence, onsetDensity, energyVariance)
character.attackRelease = lerp(быстро 5/80 мс … медленно 60/1200 мс, по motionScale)
character.beatDepth     = глубина модуляции от долей: 0 в свободном ритме … 1 в жёсткой сетке
character.flowSpeed     = скорость непрерывного движения, растёт при низком beatDepth
```

Сверху — один глобальный слайдер «Интенсивность» 0…200 %, множитель ко всей группе. Всё остальное автоматически.

## 6. Рендер

### 6.1. Общий пайплайн

- `CAMetalDisplayLink`, тройная буферизация, адаптивно 60 или 120 Гц.
- Внутренний рендер в RGBA16F, рабочее пространство Display P3 linear, тонмаппинг на выходе.
- EDR/HDR — опция; на встроенном дисплее даёт настоящую яркость вспышкам.
- Динамический `renderScale` 0.5–2.0 с автоснижением при просадке FPS.
- Переходы между пресетами: cross-fade, запуск строго на сильную долю, длительность 0–4 с.

### 6.2. Подсистема A — Feedback-растр

Буфер предыдущего кадра, warp / zoom / rotate / decay по `MusicState`, поверх — источники: осциллограмма, спектральные кольца, простые формы. Это основа классического «милкдроповского» ощущения и самая дешёвая по GPU часть.

### 6.3. Подсистема B — Векторный рендер

Полилинии с фосфорным свечением: аддитивный блендинг, послесвечение через тот же feedback-буфер с высоким decay, сканлайны и лёгкая аберрация как пост-эффект. Покрывает и ретро-осциллограф, и геометрический минимализм — разница только в источнике линий (осциллограмма против сеток и фигур Лиссажу).

### 6.4. Подсистема C — Compute-частицы

Флоу-филд на compute-шейдере, до 1 000 000 частиц, indirect draw, адвекция по полю с завихрениями, импульсы от онсетов. Самая дорогая часть — делается последней, после того как A и B доказали синхронность.

### 6.5. Бюджеты

| Сценарий | FPS | CPU | GPU | RAM |
|---|---|---|---|---|
| Окно 1600×1000 рядом с работой, подсистема A или B | 60 | ≤ 8 % | ≤ 25 % | ≤ 300 МБ |
| Полный экран 3456×2234, подсистема C | 60 | ≤ 15 % | ≤ 65 % | ≤ 700 МБ |
| Режим батареи | 30 | ≤ 6 % | ≤ 20 % | — |
| Окно скрыто или свёрнуто | 0 (пауза) | ≈ 0 % | 0 % | — |

- Пропуск кадров ≤ 0.5 % за 10 минут; ни одного xrun за 8 часов.
- Приложение работает фоном рядом с работой, поэтому **пауза при невидимом окне обязательна**, а не опциональна.

## 7. Пресеты и hot-reload

Пресеты пишутся вами через Claude Code, поэтому формат оптимизирован под правку текстом, а не под GUI-редактор.

- Пакет-директория: `preset.json` + `*.metal`. Никаких бинарных форматов.
- `preset.json`: подсистема (A/B/C), параметры с диапазонами, связки модуляции.
- **Матрица модуляции:** источник (любое поле `MusicState`, LFO, счётчик долей) → приёмник (параметр пресета), с кривой, глубиной и квантованием к сетке 1/1 … 1/16.

```json
{ "source": "beatPhase", "curve": "expOut", "target": "zoom",
  "depth": 0.35, "polarity": "bipolar", "smoothMs": 40, "quantize": "1/4" }
```

- **Hot-reload обязателен:** правка `.metal` или `.json` на диске применяется за ≤ 500 мс без перезапуска; ошибка компиляции показывается оверлеем с номером строки и текстом от компилятора Metal, старый пресет продолжает работать.
- Библиотека к 1.0: **10–12 пресетов** — по 4 на подсистемы A и B, 2–3 на C, из них минимум по одному специально под свободный ритм.
- Автосмена: выкл / по времени / по `sectionChange`; переход на сильную долю.

## 8. Интерфейс

### 8.1. Окно

Обычное окно с изменяемым размером, полный экран по `⌘F`, скрытие HUD и курсора через 3 с в полном экране, пауза при невидимом окне.

### 8.2. Хоткеи

| Клавиша | Действие | Клавиша | Действие |
|---|---|---|---|
| `Space` | Следующий пресет на сильную долю | `H` | HUD |
| `←` `→` | Пресет мгновенно | `[` `]` | A/V-смещение ∓5 мс |
| `L` | Заблокировать пресет | `C` | Режим калибровки задержки |
| `R` | Случайный | `⌘F` | Полный экран |

HUD: имя пресета, BPM с индикатором уверенности, **точка-метроном по долям** (главный инструмент проверки синхронности), применённое A/V-смещение, FPS.

### 8.3. Настройки — один экран

- Источник звука: все приложения или список выбранных.
- Общая чувствительность, отдельно бас / середина / верх.
- A/V-смещение: авто, ручная поправка, кнопка калибровки.
- Ритм: авто / только сетка / только энергия; множитель BPM ×0.5 ×1 ×2; фиксация темпа.
- Интенсивность (глобальный множитель характера, §5.5), яркость, ограничение вспышек.
- Целевой FPS, масштаб рендера, режим батареи.
- Автосмена пресетов и её период.

Всё, что тоньше этого, — в JSON пресета с hot-reload.

## 9. Тестирование

### 9.1. Юнит

DSP против эталонов: синус известной частоты → центроид; клик-трек → онсеты с точностью ≤ 3 мс; синтетический трек с известным BPM → нулевая фазовая ошибка.

### 9.2. `beatbench` — главный инструмент проекта

CLI, прогоняющий анализ по размеченному набору без GUI.

- Набор: **20 треков** — 10 электроника и техно, 6 эмбиент и классика, 4 джаз; ручная разметка долей. Берётся из вашей собственной фонотеки.
- Метрики: F-measure (окно ±70 мс), медианная и P90 фазовая ошибка, время до захвата темпа, число ложных смен темпа.

| Метрика | Порог |
|---|---|
| F-measure на электронике | ≥ 0.95 |
| F-measure на джазе | ≥ 0.75 |
| Медианная / P90 фазовая ошибка | ≤ 20 мс / ≤ 45 мс |
| Захват темпа с начала трека | ≤ 4 с |
| Ложных смен темпа за трек | ≤ 1 |
| Переход в свободный ритм на эмбиенте | ≥ 90 % случаев |

Запускается после каждого изменения в `Analysis/`.

### 9.3. Живая проверка синхронности

Точка-метроном в HUD плюс режим калибровки (§3.2). Обязательный ручной прогон на всех трёх трактах вывода: встроенные динамики, AirPods, проводной интерфейс.

### 9.4. Стабильность

Прогон 8 часов с автосменой пресетов: без утечек, без роста RSS более 5 %, без xrun'ов. Проверка бюджетов §6.5 через `powermetrics` и Metal System Trace.

## 10. Порядок работ

Оценка — в неделях работы одного человека; с Claude Code календарные сроки сжимаются, но **порядок и точки проверки менять нельзя**: каждый следующий этап опирается на доказанную работоспособность предыдущего.

| Этап | Содержание | Точка проверки | Объём |
|---|---|---|---|
| **W0** | Process Tap → RMS → цветной прямоугольник. Стабильный сертификат подписи | Звук любого плеера меняет картинку, разрешение TCC не слетает при пересборке | 3 дня |
| **W1** | Ring buffer, восстановление после смены устройств, вычисление Δout, `TimelineBus` | 8 часов без сбоев; переключение на AirPods и обратно не роняет звук | 1 нед |
| **W2** | Фичи, онсеты, темп, PLL, свободный ритм, `beatbench` | Пороги §9.2 достигнуты на вашем наборе треков | 3 нед |
| **W3** | Metal-каркас, `MusicState`, подсистема A, матрица модуляции, HUD с метрономом, калибровка Δout | Метроном визуально совпадает со слышимым битом на AirPods | 2 нед |
| **W4** | Подсистема B, формат пресетов, hot-reload | Новый пресет пишется и виден за минуты, без пересборки | 1,5 нед |
| **W5** | Подсистема C — частицы и флоу-филд | Бюджеты §6.5 в полном экране | 1,5 нед |
| **W6** | Библиотека 10–12 пресетов, настройки, автосмена, режим батареи | Все критерии §11 | 2 нед |

**Итого ≈ 11 недель** — против 20 в первой редакции ТЗ. Разница целиком за счёт отказа от `.milk`, ML, второго бэкенда захвата, дистрибуции и полной панели настроек.

Порядок неслучаен: **синхронность доказывается на этапе W3 на простейшей графике**. Если метроном не совпадает с битом на AirPods, красивые частицы этого не спасут, и всё остальное делать рано.

## 11. Критерии приёмки

1. Визуализация реагирует на звук любого приложения; разрешение выдаётся один раз и переживает пересборку.
2. Медианная ошибка попадания в долю ≤ 20 мс, P90 ≤ 45 мс на `beatbench` — **и подтверждено на слух через AirPods** в режиме калибровки.
3. На эмбиенте и классике приложение переходит в свободный ритм и выглядит осмысленно, без ложного пульса.
4. Характер реакции меняется сам между техно и эмбиентом без вмешательства пользователя (§5.5).
5. Все три рендер-подсистемы работают, библиотека 10–12 пресетов.
6. Новый пресет правится с hot-reload за ≤ 500 мс, ошибка компиляции не роняет приложение.
7. Бюджеты §6.5 выполнены, включая нулевое потребление при скрытом окне.
8. Прогон 8 часов без утечек и xrun'ов.

## 12. Риски

| # | Риск | Влияние | Митигация |
|---|---|---|---|
| R1 | **Задержка AirPods нестабильна и не всегда честно репортится** | Высокое — бьёт прямо в главную цель | Режим калибровки на слух, запоминание поправки по UID устройства, проверка на этапе W3 до всей графики |
| R2 | Свинг и рубато в джазе и классике ломают DSP-трекер | Среднее | Порог для джаза снижен до 0.75; при провале — свободный ритм вместо неверной сетки; ML остаётся запасным вариантом |
| R3 | TCC-разрешение слетает при пересборке | Среднее — тормозит разработку | Стабильный самоподписанный сертификат с первого дня, W0 |
| R4 | Три рендер-подсистемы — самый большой оставшийся объём | Среднее | Строгий порядок A → B → C; C можно отложить за пределы 1.0 без потери сути |
| R5 | Apple меняет API tap'а в macOS 27 | Низкое для личного проекта | Обновляться на новую систему после проверки |
